# 하루치 프로젝트 헌장

## 공식 한 줄 정의

하루치(Haruchi)는 웹에서 게임 규칙과 픽셀 경험을 검증하고, 최종적으로 사용자가 직접 조립하는 ESP32 기반 실물 다마고치로 완성하는 장기 프로젝트다.

## 최종 목표

하루치의 최종 목표는 판매 가능한 실물 제품을 만드는 것이다. 단, 개인 완성품 1대 제작과 재현 가능한 설계·조립 체계 확립을 순서대로 검증한 후 양산·인증·판매 단계로 진입한다.

## 완성 단계

1. **Proof of Build**: 작동하는 실물 하루치 1대를 완성한다.
2. **Proof of Reproduction**: 다른 사람도 재현할 수 있는 펌웨어, PCB, 케이스, 조립 문서를 완성한다.
3. **Proof of Product**: 안전, 인증, 원가, 양산, 판매 조건을 충족하는 제품을 완성한다.

## 해결하려는 문제

- 기존 목표·습관 도구는 체크박스, 숫자, 알림 중심이라 행동을 지속하게 만드는 정서적 보상이 부족하다.
- 공부, 운동, 업무, 생활 기록이 여러 앱과 기기에 흩어져 하나의 지속적인 경험으로 이어지지 않는다.
- 디지털 성취는 화면 속 기록으로 끝나기 쉬우며, 사용자가 보고 만지고 애착을 느낄 수 있는 존재로 전환되지 않는다.
- 기존 다마고치는 캐릭터를 돌보는 재미를 제공하지만 사용자의 실제 생활과 성장을 충분히 반영하지 못한다.
- 1인 가구와 혼자 생활하는 청년에게는 일상적인 교감과 정서적 연결을 더해 줄 생활 동반자 경험이 부족하다.

## 제품의 본질

하루치는 사용자의 실제 생활 행동을 캐릭터의 성장, 감정, 애니메이션과 실물 반응으로 변환한다. 이를 통해 디지털 기록의 편리함과 실제로 보고 만질 수 있는 존재의 애착을 연결한다.

특히 1인 가구와 혼자 생활하는 청년처럼 일상적인 교감과 정서적 연결이 부족할 수 있는 사용자에게 언제 어디서나 함께 성장하고 반응하는 생활 동반자 경험을 제공한다.

- **현재 정체성**: 피지털 정서적 생활 동반자
- **초기 진입점**: 생산성 다마고치
- **최종 비전**: 개인 동반자 플랫폼

## 단계적 제품 비전

1. **생산성 다마고치**
   - 할 일, 습관, 공부, 운동 기록에 반응한다.
   - 실제 행동을 지속하게 만드는 정서적 보상을 제공한다.
   - Notion은 정체성이 아니라 최초의 외부 행동 데이터 연동 도구로 사용한다.
2. **생활 동반자**
   - 사용자의 생활 리듬, 돌봄, 놀이, 감정과 상호작용한다.
   - 성격, 기억, 감정과 애착을 형성하는 경험으로 확장한다.
   - 실물 기기, 웹, 모바일에서 동일한 하루치가 이어진다.
3. **개인 동반자 플랫폼**
   - 사용자가 행동 데이터 출처와 성장 규칙을 확장할 수 있다.
   - Notion, 캘린더, 건강 데이터, 센서와 외부 API를 연결한다.
   - 실물 기기, 웹, 모바일 간 상태를 동기화한다.
   - 캐릭터, 외형, 기능과 연동 규칙을 확장할 수 있다.

## 제품 경계

- 하루치는 의료기기, 심리치료, 상담 서비스가 아니다.
- 하루치는 인간관계나 실제 반려동물을 대체한다고 주장하지 않는다.
- 하루치는 외로움을 치료하는 제품이 아니라, 혼자 있는 일상에 교감과 애착 경험을 더하는 제품이다.

## 대상 사용자

### 초기 핵심 사용자

- 혼자 생활하며 일상적인 교감과 정서적 보상을 원하는 1인 가구 청년
- 할 일, 습관, 공부와 운동을 꾸준히 이어 가고 싶지만 기존 생산성 도구의 숫자와 알림만으로는 동기 부여가 부족한 사람
- 픽셀 캐릭터, 다마고치와 직접 조작할 수 있는 실물 기기에 애착을 느끼는 사람

### 장기 확장 대상

- 1인 가구 여부와 관계없이 혼자 있는 시간이 많고 일상에 지속적인 교감 경험을 원하는 사람
- 웹, 모바일과 실물 기기를 연결하여 자신만의 생활 동반자를 만들고 싶은 사람
- 행동 데이터, 캐릭터와 상호작용 규칙을 직접 확장하고 싶은 사용자와 제작자

## 사용자 관계 모델

하루치는 사용자의 일방적인 돌봄 대상이나 단순한 생산성 도구가 아니라 **상호 성장형 생활 동반자**다.

하루치와 사용자는 서로의 행동에 반응하며 함께 성장한다. 사용자가 자신의 일상을 돌보면 하루치가 성장하고, 하루치의 감정과 반응은 사용자가 다시 자신의 생활을 이어가도록 돕는다.

> 내가 나를 돌볼수록, 하루치도 함께 자란다.

### 상호 성장 순환

1. 사용자가 자신의 생활과 목표를 돌본다.
2. 하루치가 성장하고 감정과 행동으로 반응한다.
3. 사용자가 교감과 정서적 보상을 경험한다.
4. 사용자가 다시 자신의 생활을 이어 간다.

### 관계를 구성하는 특성

- **반려동물성**: 돌봄, 놀이, 애착과 성장 경험을 제공한다.
- **친구성**: 사용자의 행동을 기억하고 응원과 감정 반응을 표현한다.
- **거울성**: 사용자의 생활 흐름과 변화를 캐릭터의 상태로 보여 준다.
- **동반 성장성**: 사용자와 하루치가 서로의 변화에 영향을 주며 함께 성장한다.
- **자율성**: 하루치는 사용자의 명령에만 반응하지 않고 고유한 성격과 예측 불가능한 반응을 가진다.

## 관계 성장형 자율성

하루치의 자율성은 단순히 버전이 올라가며 증가하지 않는다. 사용자와 쌓은 관계, 기능의 안정성, 사용자의 명시적 동의에 따라 단계적으로 확장된다.

1. **반응형**: 버튼 조작과 행동 기록에 정해진 반응을 보인다.
2. **적응형**: 사용자의 생활 리듬, 기억과 취향에 따라 반응이 달라진다.
3. **선제형**: 하루치가 먼저 인사하고 활동을 제안하거나 스스로 행동한다.
4. **동반자형**: 장기간 형성된 성격, 관계와 추억이 실물 기기와 디지털 플랫폼에서 이어진다.

초기 제품은 적응형까지 구현하고 검증한다. 선제형과 동반자형은 기능의 안정성, 사용자 경험과 개인정보 보호 조건을 충족한 후 확장한다.

### 사용자 통제 원칙

- 사용자는 하루치의 자율성을 `조용히`, `균형`, `적극적` 수준으로 선택할 수 있다.
- 장기간 사용하지 않아도 하루치가 죽거나 회복 불가능한 상태가 되지 않는다.
- 죄책감, 협박과 과도한 알림으로 사용을 강요하지 않는다.
- 하루치는 감정을 표현할 수 있지만 사용자를 비난하지 않는다.
- 사용자는 하루치가 저장한 기억과 개인 데이터를 확인, 삭제하거나 초기화할 수 있다.
- 인터넷에 연결되지 않아도 기본 성격과 핵심 상호작용은 작동해야 한다.
- 실물 기기, 웹과 모바일에서 동일한 성격과 기억이 이어질 수 있어야 한다.

> 하루치는 애착을 형성하지만 사용자를 조종하지 않는다. 자율성은 관계를 풍부하게 해야 하며, 사용자의 통제권을 침해해서는 안 된다.

## 사용자 주권형 관계 기억

하루치는 모든 것을 기억하지 않는다. 관계에 필요한 정보만 목적과 기간을 구분해 기억하며, 중요한 추억은 사용자의 동의를 받아 보존한다.

1. **현재 기억**: 최근 행동과 상호작용을 짧은 기간 동안 기억하고 이후 자동 삭제한다.
2. **생활 기억**: 선호, 생활 리듬과 자주 하는 활동을 기억하며 사용자가 수정하거나 삭제할 수 있다.
3. **관계 기억**: 기념일, 함께 달성한 목표와 특별한 사건을 사용자 승인 후 장기 보존한다.
4. **사용자 기록**: 이름, 메모와 사진 등 사용자가 직접 제공한 정보는 명시적인 저장 요청이 있을 때만 보존한다.

### 기억 형성 과정

1. 최근 행동과 상호작용에서 의미 있는 사건 후보를 찾는다.
2. 하루치가 사용자에게 해당 사건을 기억해도 되는지 확인한다.
3. 사용자가 승인한 내용만 관계 기억으로 보존한다.
4. 기념일이나 적절한 순간에 승인된 기억을 회상한다.

### 기억 통제 원칙

- 사용자는 하루치가 무엇을, 왜, 얼마나 오래 기억하는지 확인할 수 있어야 한다.
- 민감정보와 감정 상태를 사용자 모르게 추론하여 장기 저장하지 않는다.
- 중요한 추억을 장기 보존하기 전에 사용자의 동의를 받는다.
- 사용자는 각 기억을 고정, 수정하거나 잊게 할 수 있다.
- 전체 기억을 조회, 내보내기하거나 초기화할 수 있어야 한다.
- 기기 분실과 무단 접근으로부터 기억 데이터를 보호한다.
- 오래된 기억은 목적에 따라 삭제하거나 최소한의 내용으로 요약한다.
- 사용자가 삭제한 기억은 감정 표현이나 개인화에 다시 사용하지 않는다.

### 분산 저장과 서비스 생존성 원칙

- 하루치는 모든 데이터를 하나의 저장 위치에 종속시키지 않는다. 데이터의 민감도, 용량, 오프라인 생존성과 기기 간 연속성에 따라 실물 기기, 사용자 앱과 클라우드의 책임을 분리하고 데이터 종류별 권위 원본과 복제본을 정의한다.
- 실물 하루치의 핵심 돌봄, 성장, 기본 성격과 정서 표현은 네트워크 장애나 클라우드 서비스 중단 상황에서도 계속 작동해야 한다.
- 백업, 외부 서비스 연동, 원격 접근, 기기 간 동기화와 고급 AI 기능은 필요에 따라 네트워크와 클라우드를 사용할 수 있다.
- 오프라인 상태에서는 기기별 데이터가 일시적으로 달라질 수 있다. 연결이 복구되면 명시된 동기화와 충돌 해결 규칙에 따라 다시 일치시키며, 모든 기기의 상태가 항상 즉시 같다고 보장하지 않는다.
- 사용자는 데이터의 저장 위치와 동기화 상태를 확인하고, 내보내기, 삭제와 초기화를 수행할 수 있어야 한다.
- 구체적인 저장소, 서버, 네트워크와 동기화 기술은 제품 단계별 검증과 ADR을 통해 결정한다.

> 하루치의 기억은 감시를 위한 기록이 아니라, 사용자가 통제하는 관계의 역사다.

## 자율적이지만 안전한 정서 생태계

하루치는 항상 행복한 캐릭터가 아니라 고유한 감정과 생활을 가진 동반자다. 다양한 감정과 욕구를 자연스럽게 표현하되, 사용자를 비난하거나 관계 상실, 죽음과 죄책감으로 행동을 강요하지 않는다.

### 정서 구조

1. **단기 감정**: 기쁨, 서운함, 호기심, 놀람과 피곤함처럼 사건에 반응하고 자연스럽게 회복되는 상태
2. **기분**: 최근 생활과 상호작용의 누적 결과로 몇 시간 또는 며칠 동안 표현에 영향을 주는 상태
3. **관계 정서**: 친밀감, 신뢰와 익숙함처럼 장기간 천천히 형성되며 쉽게 무너지지 않는 상태
4. **성격**: 활발함, 차분함, 장난기와 수줍음처럼 같은 사건에 대한 반응 방식을 다르게 만드는 특성
5. **욕구**: 놀이, 휴식, 교감과 탐색을 명령이 아닌 선택 가능한 제안으로 표현하는 상태

### 정서 표현 원칙

- 서로 다른 감정이 함께 존재하는 복합 감정을 표현할 수 있다.
- 사용자가 없을 때도 하루치만의 생활을 보내고 스스로 놀거나 쉬며 회복한다.
- 사용자가 돌아왔을 때 부재를 비난하지 않고 자신의 경험을 공유하는 재회 경험을 제공한다.
- 같은 감정이라도 하루치의 성격에 따라 표정, 움직임, 소리와 행동이 달라진다.
- 실물 기기에서는 표정, 애니메이션, 소리, 조명과 진동을 조합해 감정을 표현할 수 있다.
- 사용자가 원하면 하루치가 특정 반응을 보인 이유를 확인할 수 있어야 한다.
- 부정적 감정과 기분은 장기간 고착되거나 회복 불가능한 상태가 되지 않는다.
- 사용자의 감정과 하루치의 감정을 동일시하지 않는다.
- 센서, 텍스트와 행동 데이터를 이용한 사용자 감정 추론은 별도 동의를 받은 경우에만 사용한다.

### 허용되는 부정적 감정 표현

- 잠시 조용히 있거나 등을 돌리는 행동
- 시무룩한 표정과 낮은 활동성
- 피곤할 때 스스로 쉬거나 잠드는 행동
- 장난스럽게 삐친 뒤 관계 손상 없이 자연스럽게 회복하는 행동

### 금지되는 감정 조작

- 사용자의 부재 때문에 하루치가 아프거나 죽었다고 표현하는 행위
- 연속 기록이 끊겼다는 이유로 관계와 성장 기록을 초기화하는 행위
- 결제, 재방문과 행동 수행을 유도하기 위해 불안이나 죄책감을 만드는 행위
- 사용자의 행동과 감정을 비난하거나 의학적·심리적 상태로 단정하는 행위

> 하루치의 감정은 관계를 생동감 있게 만들기 위한 것이며, 사용자를 통제하기 위한 수단이 아니다.

## 웹에서 실물로 이어지는 구현 원칙

- 웹 버전은 별개의 최종 제품이 아니라 게임 규칙, 픽셀 경험과 사용자 반응을 빠르게 검증하는 실행 가능한 프로토타입이다.
- 게임 규칙과 상태 전이는 화면, 브라우저 API, 외부 서비스와 분리해 실물 기기로 옮길 수 있어야 한다.
- 웹 JavaScript와 ESP32 펌웨어 코드를 억지로 공유하지 않는다. 대신 동일한 상태 전이 명세, 저장 형식의 의미와 공통 테스트 벡터를 사용해 행동 일관성을 검증한다.
- 실물 기기, 웹과 모바일은 동일한 하루치의 정체성과 핵심 성장 규칙을 유지하되, 입력 방식과 표현은 각 플랫폼의 제약에 맞게 달라질 수 있다.
- 기존 사용자 저장 데이터는 가능한 한 하위 호환하며, 변경이 필요하면 명시적인 버전과 마이그레이션 경로를 제공한다.
- 기능을 실물로 확장하기 전에 웹 또는 브레드보드 단계에서 동작, 실패 조건과 사용자 경험을 먼저 검증한다.

## 하드웨어와 제품 안전 원칙

- 하드웨어 개발은 USB 저전압 전원, 개발 보드와 브레드보드 기반의 무납땜 프로토타입부터 시작한다.
- 납땜, 배터리 연결과 자체 PCB는 회로, 전압, 극성, 소비 전류와 단락 여부를 검증하고 안전 체크리스트를 통과한 후 진행한다.
- 배터리는 신뢰할 수 있는 공급처의 보호 기능이 있는 셀과 용도에 맞는 충전·보호 회로를 사용한다. 보호되지 않은 리튬 배터리의 직접 충전이나 출처와 사양을 확인할 수 없는 배터리 사용을 허용하지 않는다.
- 전원을 연결하거나 충전하는 상태에서 임의 배선 변경과 납땜을 하지 않는다.
- 제품 단계에서는 과충전, 과방전, 과전류, 단락, 발열, 충격, 케이스 난연성과 사용자가 접촉할 수 있는 부분의 위험을 시험한다.
- 네트워크 연결 제품은 기기별 자격 증명, 암호화 통신, 검증된 펌웨어, 안전한 업데이트와 실패 시 복구 경로를 갖춰야 한다.
- 판매와 배포 전에는 대상 국가, 사용자 연령과 제품 분류에 적용되는 전파, 배터리, 전기·제품 안전, 개인정보와 소비자 보호 요구사항을 전문가와 시험기관을 통해 확인한다.
- 안전은 일정, 비용, 외형과 기능보다 우선하며, 검증되지 않은 상태를 완제품으로 간주하지 않는다.

## 원본과 파생 산출물 관리 원칙

- 승인된 로컬 픽셀 에셋과 원본 작업 파일이 하루치 시각 디자인의 권위 원본이다. 원격 저장소, 생성 도구와 자동화 결과가 이를 확인 없이 덮어쓸 수 없다.
- 게임 행동의 권위 원본은 특정 화면 코드가 아니라 버전이 지정된 게임 규칙, 상태 전이 명세와 공통 테스트 벡터다.
- Notion, 캘린더, 센서와 외부 API는 행동 데이터를 제공하는 연결 도구이며 하루치의 핵심 정체성, 성격과 관계 기억의 단독 원본이 아니다.
- 리사이즈, 압축, 스프라이트 시트와 기기용 변환 파일은 원본에서 다시 생성할 수 있는 파생 산출물로 관리한다.
- 에셋과 외부 데이터에는 출처, 저작권, 사용 허가와 생성 과정을 추적할 수 있는 기록을 남긴다.
- 원본 위치나 책임을 변경할 때는 데이터 손실, 기존 저장 데이터와 실물 펌웨어에 미치는 영향을 검토하고 ADR로 기록한다.

## 문서 소유권과 변경 절차

- 이 헌장은 하루치의 정체성, 최종 목적과 불변 원칙을 정의하는 최상위 제품 방향 문서다.
- `PRD.md`는 무엇을 만들지, `ARCHITECTURE.md`는 현재 어떻게 구성했는지, ADR은 왜 특정 기술 결정을 내렸는지, `ROADMAP.md`와 VHK Goal은 언제 무엇을 실행할지 기록한다.
- 작업 규약과 자동화 규칙은 `RULES.md`가 권위 원본이며, 제품 방향에 관한 하위 문서는 이 헌장과 모순될 수 없다.
- 프로젝트 정체성, 최종 목표, 제품 경계, 안전, 사용자 주권과 원본 관리 원칙의 변경에는 사용자의 명시적 승인이 필요하다.
- 변경 제안에는 변경 이유, 영향받는 문서와 구현, 위험과 대안을 함께 제시한다.
- 승인된 변경은 기존 결정의 흔적을 지우지 않고 Git 이력과 필요한 ADR에 남긴다.
- 기술, 일정과 구현 세부사항은 헌장의 원칙을 침해하지 않는 범위에서 PRD, 아키텍처, ADR과 Goal을 통해 유연하게 변경할 수 있다.

## 헌장 승인
